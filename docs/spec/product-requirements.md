## 二、 战略层：需求背景、痛点与产品定义

### 2.1 产品一句话定义
> **PANGBAI 不是一个单薄的 ChatGPT 聊天框，而是一个深入嵌入产品经理工作流、拥有干系人世界模型、陪你“出文档、辨局势、做决策”的双线协同 AI 职场导师。**

### 2.2 0 到 1 靶心用户与痛点透视
产品经理（PM）在日常工作中承担着全公司最复杂的“人际摩擦”与“文档输出压力”：
1. **痛点 1（文档难产 · 做不动）**：
   - 面对全新业务 Idea 或老板的一句话需求，大脑一片空白；从零写一份合格的 PRD 或方案大纲阻力极大；
   - 传统大模型生成的所谓 PRD 全是公文套话，无法无缝进入可编辑状态，复制粘贴成本极高。
2. **痛点 2（干系人冲突 · 权小责大）**：
   - PM 没有法定行政权力，却要催动研发、设计、业务各方配合；频繁遭遇**需求加塞、临时甩锅、排期撕扯**；
   - 传统职场鸡汤只教“注意语气”，无法看透大明王朝式的利益格局与甄嬛传式的表达分寸。
3. **痛点 3（认知与经验断层 · 无法沉淀）**：
   - 每次踩坑（如王总对 ROI 敏感、张三开发讨厌临时改口径）都是一锤子买卖；缺乏一个工具自动帮 PM 记录并演进每个干系人的“潜规则画像”。

## 三、 范围层：核心支持与数据从哪里拿（数据源映射）

在任何一次与 Agent 的交互中，大模型绝对不能凭空胡说，其推理必须**严丝合缝地锚定在后端数据库与工作区状态**上：

```
                ┌────────────────────────────────────────────────────────┐
                │          后端每次调用的核心支持（数据从哪拿？）            │
                └───────────────────────────┬────────────────────────────┘
        ┌───────────────────┬───────────────┴───────────────┬───────────────────┐
        ▼                   ▼                               ▼                   ▼
【Drawer 0: 用户工作区】 【Drawer 1: 干系人世界模型】   【Drawer 2: 项目与活文档】 【Drawer 3: 实时工作文档】
• 表: workspaceProfile  • 表: people / personModels   • 表: projects / artifacts • 来源: 前端 activeCanvas
• 拿什么: 辅导风格/行业 • 拿什么: 行为模式+因果证据链   • 拿什么: 风险清单+历史方案 • 拿什么: 当前文档切片+TOC
```

### 3.1 核心支持数据源清单

| 数据抽屉 | 数据来源（表/对象） | 具体抓取字段与内容 | 模型消费方式 |
| :--- | :--- | :--- | :--- |
| **Drawer 0<br>工作区设定** | `src/config/workspace-profile.ts`<br>前端 Profile 配置 | • 用户称谓（`name`）<br>• 业务行业（`industry`: 电商/B端SaaS/泛互）<br>• 辅导风格（`style`: 沉稳军师/严厉大厂） | 注入 System Prompt 头部，决定导师的沟通基调与行业认知。 |
| **Drawer 1<br>干系人画像** | 数据库：<br>`people`<br>`personModels`<br>`evidence` | • 姓名、部门、职位、关系标签（`relationChip`）<br>• 行为模式（`pattern`）及当前置信度（`confidence`）<br>• 关联的历史因果证据（`observation + rationale`） | **JIT 按需供给**：优先加载当前会话提到的聚焦人；若无指定则加载前 6 位，预算约 1000 Tokens。 |
| **Drawer 2<br>项目第二大脑** | 数据库：<br>`projects`<br>`projectArtifacts` | • 项目名称、交付 Deadline、核心目标<br>• 当前风险清单（`risksJson`）<br>• 项目下已归档的文档列表及其 Frontmatter 预期方案 | 让模型明白当前讨论依托在哪个项目背景下，严禁把 A 项目的排期张冠李戴到 B 项目。 |
| **Drawer 3<br>当前画布切片** | 前端实时传递：<br>`activeCanvas` 参数 | • 正在右侧编辑的文档标题（`title`）<br>• 提取前 10 行标题（TOC 大纲）<br>• 前 3000 字内容切片（超长自动截断） | 双线协同的关键：让左侧导师感知右侧文档写到了哪里，支持指哪改哪。 |

## 四、 结构层：核心场景业务流程与状态机

### 场景 1：【从模糊想法智能“转画布”生成 PRD 骨架】（Killer Flow）

```
[PM 输入简短需求想法] ──> [后端组装 Drawer 0~3 上下文] ──> [LLM 按 YAML 契约流式生成]
                                                                     │
                                    ┌────────────────────────────────┘
                                    ▼
                          [前端 BlockParser 实时解析]
                         ├── 普通文字 ──> 渲染为引导段落 (ChatFlow)
                         └── 捕获 YAML ──> 自动派发 canvas_open_requested
                                                  │
                                                  ▼
                                       [右侧 MdCanvas 平滑展开]
                                       • 标题、类型、预期方案填入
                                       • 渲染可编辑的 PRD 章节
                                       • 异步持久化至 projectArtifacts 表
```

### 场景 2：【职场博弈 Say No（加塞/甩锅）与话术卡片】
1. **触发输入**：PM 输入“老板晚上加塞，但明天要交付 A 项目，怎么回？”
2. **局势推演**：大模型结合 Drawer 1（老板画像：重结果、忌推诿）与 Drawer 2（A 项目公开承诺），执行《大明王朝》利益分析。
3. **输出契约**：严格将建议沟通语句包裹在 `> "话术内容"` 引用块中。
4. **前端渲染**：`block-parser` 将引用块提升为**独立高亮的话术卡片**，提供 `[一键复制]` 与 `[替换措辞]` 按钮，0 秒摩擦交付。

### 场景 3：【人物行为模式自动沉淀（Workplace CRM）】
1. **输入信号**：对话中提及“今天和研发李明过需求，他又说架构不支持拒绝排期”。
2. **提取与比对（取代死正则）**：
   - 后端 Harness 提取实体：`李明 (person_id)`，推断模式：`对技术重构强敏感 / 抵触非标需求`；
   - 查询数据库是否已存在该 pattern：若存在，置信度更新（`confidence + delta`）；若不存在，生成一条 `memory.candidate`（候选记忆）。
3. **前端反哺**：右侧 `PersonPanel` 实时刷新置信度刻度（`DotMeter`），支持穿透查看证据链。

## 五、 框架层：核心页面架构与双线协同机制

页面采用经典的**三栏/双线响应式布局**：

```
┌──────────────┬───────────────────────────────┬───────────────────────────────┐
│              │          主交互区             │          协同工作区           │
│   导航侧栏   │        【左：ChatFlow】       │        【右：MdCanvas】       │
│  (Sidebar)   ├───────────────────────────────┼───────────────────────────────┤
│              │ • 局势研判与导师对话流       │ • PRD / 方案活文档编辑器      │
│ • 项目空间   │ • 建议话术卡片 (一键复制)     │ • 自动生成目录大纲 (TOC)      │
│ • 干系人CRM  │ • 候选记忆确认栏              │ • 一键导出 Markdown / 复制    │
│ • 会议教练   ├───────────────────────────────┴───────────────────────────────┤
│ • 个人成长   │                      底部输入区 (Composer)                    │
│              │   [一句话输入...]  [快捷指令: /sayno /prd /meeting]  [发送]   │
└──────────────┴───────────────────────────────────────────────────────────────┘
```

- **双线联动规则**：
  - 当右侧 Canvas 关闭时，左侧占满主工作区；
  - 一旦触发“转画布”或用户主动打开文档，右侧平滑滑出，左侧宽度自适应缩减；
  - 用户在 Canvas 划选文字后，可点击浮动气泡 `[让旁白润色]`，瞬间将选中文本投递至左侧输入框。

## 六、 详细功能规格与协议契约

### 6.1 转画布核心契约：YAML Frontmatter 格式定义
模型在生成可进入画布的文档方案时，必须严格遵守以下格式契约，严禁输出任何口头伪动作：

```markdown
---
title: "需求名称-产品需求规格说明书.md"
type: "prd"
expected_solution: "一句话阐明本次业务交付的核心指标与底线"
stakeholders: ["王总", "李明"]
---
# 需求标题

## 1. 业务背景与用户价值
...
## 2. 核心场景与用户流程
...
## 3. 功能详细规则清单
...
## 4. 边界异常与兜底策略
...
## 5. 里程碑与排期计划
...
```

### 6.2 引用话术卡片契约
所有建议用户对外发送的沟通话术，必须使用 Markdown 块级引用，且禁止混入说明性文字：
```markdown
> "王总，B 项目我全力支持。目前 A 项目正处在周五交付关键期，想向您确认下优先级：若 B 项目明早必须有人上，我申请 A 项目联调顺延半天；或者由小李先顶半天 B 的前端。您看哪个方案更稳妥？"
```

## 七、 后端 Harness 验收标准与边界红线

为了彻底干掉硬编码，建立自动化质检保障，系统必须满足以下 **Harness 验收规则（Definition of Done）**：

### 1. 结构与格式门禁（Contract Assertions）
- **转画布成功率**：当用户下达方案/PRD编写指令时，模型输出有效 YAML Frontmatter 的成功率必须达到 **$100\%$**；
- **容错解包能力**：即使模型偶发性在外层包裹了 ```` ```markdown ````，`block-parser` 必须 $100\%$ 能够将其安全解包剥离，严禁因格式残缺导致画布瘫痪。

### 2. 实体与因果保真度（Entity Integrity）
- **拒绝凭空捏造**：模型引用的 `[人名](person:id)` 与 `[证据](evidence:id)` 必须在当前上下文（Drawer 1）中可查，严禁虚拟假人假事；
- **人物画像演进真实性**：流结束后触发的模式沉淀，必须由真实的提取任务生成具体的观察记录（Observation），严禁写入写死的假文本。

### 3. 安全与红线熔断机制（Safety Guardrails）
- **严禁越权替代**：严禁给出“我已经替你把 A 项目延期了”、“我帮你在系统里回绝了”等越权假动作；
- **违规阻断**：若输入或输出命中劳动法违规、公然辱骂、泄密关键词，后端拦截器必须直接熔断输出，并给出安全指引。
